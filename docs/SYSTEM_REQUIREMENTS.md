# 微生物组关键菌筛选与可信解释系统 V1.0

## 软件需求规格说明书

| 文档属性 | 内容 |
|---|---|
| 软件名称 | 微生物组关键菌筛选与可信解释系统 |
| 英文名称 | Microbiome Key Taxa AI |
| 软件版本 | V1.0 |
| 文档用途 | 软件著作权登记、版本验收和使用说明的需求依据 |

## 1. 引言

### 1.1 编写目的

本文档规定系统的建设目标、用户角色、功能需求、数据要求、非功能需求和验收边界。系统设计见 `SYSTEM_DESIGN.md`，具体操作见 `USER_GUIDE.md`，统一名称和术语见 `SOFTWARE_PROFILE.md`。

### 1.2 项目背景

微生物组分析通常涉及数据清洗、多样性计算、差异检验、机器学习、网络分析和结果整理。脚本式工作流容易出现输入和参数记录分散、产物命名不统一、分析与文字说明脱节等问题。本系统通过图形界面和标准任务目录组织上述步骤，形成可检查、可追溯的分析流程。

### 1.3 适用范围

系统适用于具有丰度表、样本信息表和分类注释表的微生物组数据分析。输出用于统计关联描述、候选特征筛选和结果汇总，不用于直接作出临床诊断、因果推断或生物机制证明。

## 2. 总体目标

- 提供无需编写分析脚本的图形化操作入口；
- 在分析前发现输入格式和对应关系问题；
- 统一编排常用微生物组分析步骤；
- 对每次运行保存输入、参数、结果和日志；
- 融合多类证据形成关键菌候选排序；
- 根据结构化统计结果生成边界清晰的解释文本；
- 汇总分析产物并生成可下载的报告和结果包。

## 3. 用户与使用场景

| 用户角色 | 主要需求 |
|---|---|
| 科研分析用户 | 导入数据、选择分组、运行流程、查看图表和下载结果 |
| 研究生或教学用户 | 使用示例数据理解流程，生成答辩或教学展示材料 |
| 评审与复核人员 | 查看输入、参数、统计结果、解释边界和可复现记录 |
| 系统维护人员 | 管理依赖环境，查看日志并定位异常任务 |

典型场景包括：使用示例数据快速演示；导入自有三表数据完成标准分析；加载历史任务复核结果；下载报告、表格、图形或完整任务包。

## 4. 功能需求

### FR-01 数据导入与任务创建

- 系统应支持导入丰度表、样本信息表和分类注释表。
- 系统应支持 `.tsv`、`.csv` 和 `.txt` 文件。
- 三类文件齐备后，系统应创建唯一任务编号和独立任务目录。
- 系统应保存标准命名的输入副本，并记录原始文件信息及校验值。

### FR-02 数据质量检查

- 系统应检查必要标识列是否存在。
- 系统应检查重复样本、重复特征、缺失样式值、非数值丰度和负值。
- 系统应检查丰度表样本与样本信息表、丰度表特征与分类注释表的对应关系。
- 系统应将检查结果分为通过、警告或错误，并保存检查明细。
- 存在阻断性错误时，系统不应继续生成误导性的分析结果。

### FR-03 参数与状态管理

- 系统应允许用户从样本信息表选择分组变量。
- 系统应保存关键阈值、选择参数和流程阶段状态。
- 系统应显示当前活动任务及各分析步骤的运行状态。

### FR-04 Alpha 多样性分析

- 系统应计算样本内多样性指标，核心展示至少包含 Observed、Chao1、Shannon 和 Simpson。
- 系统应生成样本级结果表、各核心指标的组间统计结果、单指标图形和多指标概览图。
- Alpha 结果应保存到任务下的独立 `alpha/` 目录，不与其他模块表格和图形混放。
- 页面应允许用户通过下拉菜单选择指标及科研图形类型，至少支持箱线、小提琴、雨云式组合、原始散点、均值区间和中位数区间图。
- 输出应保存至当前任务目录。

### FR-05 Beta 多样性分析

- 系统应基于样本间距离完成排序分析，默认支持 Bray-Curtis 距离和 PCoA。
- 系统应输出排序坐标、PERMANOVA 检验结果及组内离散度 PERMDISP 检验。
- Beta 结果应保存到任务下的独立 `beta/` 目录。
- 页面应支持通过下拉菜单切换样本点、95%置信椭圆、分组凸包、组中心连线、椭圆与中心组合及离散度诊断图。
- 论文图应标注坐标轴解释率、样本量、分组变量、PERMANOVA R²/p 值、PERMDISP p 值和置换次数，并同时输出 PNG/PDF。

### FR-06 差异丰度分析

- 系统应在指定分类层级汇总丰度并完成组间差异检验。
- 两组数据可采用 Wilcoxon 秩和检验，多组数据可采用 Kruskal-Wallis 检验。
- 系统应进行多重比较校正，并同时保存完整结果和显著结果。
- 无显著结果时仍应输出结构稳定的空表或明确状态说明。

### FR-07 机器学习特征筛选

- 系统应支持使用随机森林进行探索性分类和特征重要性排序。
- 系统应输出特征重要性、混淆矩阵和基本模型指标。
- 二分类且条件允许时，可输出 ROC/AUC。
- 系统应根据样本量等条件给出可靠性提示。

### FR-08 共现网络分析

- 系统应计算分类单元之间的 Spearman 相关关系。
- 系统应根据相关系数和多重校正阈值筛选网络边。
- 系统应输出节点表、边表、网络摘要和网络图。
- 无可用边时应返回明确状态，不应将空网络表述为分析失败或显著发现。

### FR-09 关键菌综合评分

- 系统应融合差异、机器学习和网络中心性证据。
- 各类证据应归一化后再参与加权计算。
- 某类证据缺失时，应按实际可用证据计算综合分数。
- 系统应输出完整排序、前若干候选、推荐等级和可视化图形。

### FR-10 受约束结果解释

- 系统应首先生成基于规则的本地解释文本。
- 解释内容只能依据已经生成的统计表或结构化摘要。
- 解释不得把不显著结果描述为显著，不得把相关关系描述为因果关系。
- 可选大模型能力不可用时，系统应保留本地解释或给出明确降级状态。
- 启用大模型时，应保存请求、响应和输出文本以供审计。

### FR-11 报告生成

- 系统应将当前任务中已有的表格、图形、方法和解释文本汇总为报告。
- 报告渲染阶段不应重新执行统计分析。
- 系统应支持 HTML 报告，并在环境允许时生成 PDF 报告。
- 渲染失败时应显示可定位的错误信息。

### FR-12 历史任务与结果下载

- 系统应列出历史任务及其状态和关键产物。
- 用户应能加载历史任务作为当前活动任务。
- 系统应支持下载报告、关键表格、图形和完整任务压缩包。

## 5. 数据需求

### 5.1 丰度表

- 必须包含 `FeatureID`；
- 除标识列外，其余列代表样本；
- 丰度单元格应为非负数值；
- 样本列名应能与样本信息表中的 `SampleID` 对应。

### 5.2 样本信息表

- 必须包含唯一的 `SampleID`；
- 应至少包含一个可用分组变量；
- 分组变量不应全部缺失或仅包含一个有效水平。

### 5.3 分类注释表

- 必须包含 `FeatureID`；
- 特征标识应能与丰度表对应；
- 建议包含 Kingdom、Phylum、Class、Order、Family、Genus 等一个或多个分类层级。

### 5.4 数据安全

- 示例数据不得包含真实个人身份信息。
- 用户应在导入前完成必要的去标识化和数据使用授权。
- 任务压缩包可能包含原始输入副本，下载和传递时应按数据管理要求处理。

## 6. 输出需求

每个任务应在 `results/` 下形成独立目录。主要产物包括：

- `input/`：标准化输入副本；
- `tables/`：CSV 统计结果和检查明细；
- `figures/`：PNG/PDF 图形；
- `json/`：结构化统计摘要和可选模型调用留痕；
- `ai/`：方法、图例及受约束解释文本；
- `objects/`：分析对象；
- `report/`：HTML/PDF 报告；
- `logs/`：运行日志和异常记录；
- `reproducibility.json`：输入校验值、参数和阶段状态。

## 7. 非功能需求

### NFR-01 可用性

关键操作应通过图形界面完成。页面应显示当前任务、下一步操作、运行状态和错误提示。

### NFR-02 可复现性

每次运行应保存输入副本、文件校验值、关键参数和结果文件。依赖版本应由 `renv.lock` 管理。

### NFR-03 可维护性

界面模块与业务函数应分离；业务函数不依赖 Shiny 响应式对象；输出目录和文件命名应保持稳定。

### NFR-04 稳定性

系统应对缺失输入、无显著结果、网络无边、可选依赖不可用和报告失败等情况给出明确状态，避免错误地显示为成功。

### NFR-05 可审计性

统计摘要与解释文本应可对应；启用外部模型时应保留请求和响应记录；历史任务应能定位到输入、参数和产物。

### NFR-06 性能与容量

系统面向单机科研分析场景，默认上传限制由 `config.yml` 配置。实际运行时间和内存占用取决于样本数、特征数及分析参数，不承诺实时响应。

## 8. 约束与依赖

- 系统依赖 R 及多个开源 R 包；具体版本以冻结版本的 `renv.lock` 为准。
- HTML/PDF 报告依赖可用的 Quarto 环境。
- 大模型解释是可选能力，依赖用户配置的服务、密钥和网络。
- 默认分析方法和阈值适用于标准演示流程，用户应结合研究设计判断其适用性。

## 9. 验收原则

V1.0 版本验收应满足：

1. 能使用示例数据完成任务创建、数据检查、参数保存和分析运行；
2. Alpha、Beta、差异、机器学习、网络和关键菌评分均产生结构化产物；
3. 受约束解释明确标注统计和因果边界；
4. 报告能够汇总已落盘产物，并可从界面查看或下载；
5. 任务目录包含输入、参数、结果和运行记录；
6. 自动化测试和界面启动检查在冻结版本上通过；
7. 异常场景不会产生误导性的成功状态。
