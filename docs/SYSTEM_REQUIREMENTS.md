# SYSTEM REQUIREMENTS（系统需求规格说明）

面向对象：硕士毕业论文支撑材料 / 系统验收材料  
适用范围：本仓库现有 R Shiny 系统（不涉及新增功能与代码修改）  
说明：本文件从“需求”角度描述系统应满足的能力与边界；实现细节与流程说明请分别参考 `docs/SYSTEM_DESIGN.md` 与 `docs/USER_GUIDE.md`。

## 1. 研究背景与问题定义

微生物组研究中，常见的分析任务包括 Alpha/Beta 多样性、组间差异丰度、标志菌筛选、共现网络探索等。传统工作方式多依赖脚本式分析与人工整理结果，存在以下工程性痛点：

- 多步骤流程分散，数据输入、参数记录、产物组织与报告汇总容易不一致，影响复现与交付。
- 面向非程序背景用户时，上手门槛较高；不同分析环节的结果分散在多处文件，难以快速验收与展示。
- “解释性文本”容易与统计结果脱节，且存在过度推断（因果/机制推断）风险。

本系统聚焦于将既有统计分析能力进行工程化编排与可复现输出组织，以支撑答辩展示与系统验收。

## 2. 系统建设目标

系统建设目标以“可用、可复现、可验收”为主，不以提出新统计方法为目标：

- 提供基于 R Shiny 的交互入口，使用户可完成：数据上传 → 校验 → 参数选择 → 一键分析 → 结果预览 → HTML 报告输出。
- 对每次运行建立独立的作业目录（job），固化输入、参数与产物，形成最小可复现实验单元。
- 将核心统计结果以结构化文件（表格/JSON）与图形方式落地，并汇总为可交付的 HTML 报告。
- 对 AI 文本解释施加约束：仅允许基于系统已生成的结构化统计产物进行“摘要式说明”，并明确不进行因果或机制结论输出。

## 3. 用户角色

- 研究生/研究者（主要用户）：上传数据、选择分组变量、运行流程、阅读结果与报告，用于论文图表与附录材料整理。
- 指导教师/评审（验收用户）：关注流程是否完整、结论表达是否边界清晰、产物是否可追溯与可复现。
- 系统维护者（运维/开发）：关注依赖环境、稳定性、日志与错误定位；不要求频繁改动分析方法。

## 4. 功能性需求

本节以“系统应当支持/输出什么”为准，细节实现可参考设计文档与用户手册。

### 4.1 数据上传

- 支持上传三类输入表：abundance（丰度/特征表）、metadata（样本信息表）、taxonomy（分类注释表）。
- 支持常见文本格式：`.tsv/.csv/.txt`，首行为表头。
- 上传后应创建独立 job 目录并固化输入文件（避免后续依赖用户原始文件路径）。

### 4.2 数据校验

- 在进入分析前提供强制性的 Data Check 步骤。
- 校验应覆盖：必要列存在性、样本/特征对齐、缺失值/重复标识、基本数值合法性（如非负）。
- 校验结果应以表格形式落地，供验收与复核。

### 4.3 参数选择

- 允许用户从 metadata 中选择分组变量（`group_var`）。
- 关键参数应被记录到可复现记录文件中，用于复盘与对比。

### 4.4 Alpha diversity

- 计算并输出至少一个核心 Alpha 指标（系统以 Shannon 作为必备展示指标）。
- 提供组间统计检验与可视化，并输出表格与图形文件。
- 解释边界：只报告统计关联，不推断因果。

### 4.5 Beta diversity

- 计算样本间距离并进行降维展示（系统采用 Bray-Curtis + PCoA 的固定实现）。
- 提供组间差异检验（如 PERMANOVA）并落地表格结果。
- 解释边界：仅反映距离矩阵层面的组间差异，不等同于机制解释。

### 4.6 差异丰度分析

- 在指定分类层级（系统默认 Genus）上进行组间差异检验。
- 输出完整结果表与显著结果表（即使无显著结果也应生成占位表以保证流程稳定）。
- 输出结构化汇总（JSON）与可视化图（如 volcano / barplot）。

### 4.7 AI 可信解释

- 系统应提供“受约束的解释文本”产物，且必须满足：
  - 解释仅基于已生成的统计产物（表格/JSON）进行摘要说明。
  - 明确包含免责声明：不输出因果/机制结论，不把不显著结果表述为显著。
- 解释文本应作为独立文件落地，并可被最终报告引用。

### 4.8 机器学习标志菌筛选

- 提供探索性的监督学习筛选能力（系统使用 Random Forest）。
- 输出特征重要性与基本模型指标（如混淆矩阵/accuracy；二分类时可输出 ROC/AUC）。
- 必须给出“可靠性提示”（如基于样本量的 caution 分级），强调探索性用途。

### 4.9 共现网络分析

- 提供基于相关性（Spearman）的共现网络构建与可视化。
- 支持阈值筛边（相关系数阈值与多重校正阈值），并输出 nodes/edges 表与汇总 JSON。
- 明确解释边界：相关不等于因果，网络边不应被解释为直接相互作用证据。

### 4.10 Key Taxa Score

- 将差异分析、机器学习重要性、网络中心性等证据进行归一化后融合，形成候选关键菌的工程化排序指标。
- 输出完整打分表与 Top 列表，并给出分级（如 High/Medium/Low）。
- 明确用途：用于候选优先级排序与展示，不等同于生物学因果“关键性”证明。

### 4.11 HTML 报告生成

- 基于 Quarto 模板将 job 目录中的既有产物汇总为 `report.html`。
- 报告应可重复渲染（同一 job 目录在相同环境下多次渲染内容一致），并在报告中呈现：
  - 主要图表与关键表格（或其引用）
  - 方法与图例文本
  - 可复现记录（输入、参数、关键阈值等）
- 报告生成阶段不应引入新的统计分析步骤。

### 4.12 结果文件管理

- 每次运行的所有产物应集中保存在对应 job 目录中（包括输入副本、表格、图形、JSON、AI 文本、报告与日志）。
- 产物路径应稳定、可被验收人员按规则定位，不依赖临时路径或交互状态。

## 5. 非功能性需求

### 5.1 可用性

- 面向非程序用户：以 Shiny 页面完成关键操作，提供明确的操作顺序与提示信息。
- 失败时应给出可定位的信息（如提示查看 job 下的错误日志）。

### 5.2 可复现性

- 每次运行创建独立 job 目录作为复现实验单元。
- 输入文件应被固化保存，并记录校验信息（如 MD5/文件名等）与关键参数。
- 依赖环境应可锁定与恢复（本项目使用 `renv.lock`）。

### 5.3 可解释性

- 统计结果与解释文本之间应可追溯：解释必须来源于结构化统计产物。
- 在所有涉及“解释”的环节中，必须给出边界声明（不因果、不机制、不夸大显著性）。

### 5.4 稳定性

- 当某些环节无显著结果、网络稀疏或无法形成边时，应仍输出占位表/占位图（或明确提示），避免流程中断。
- 输出文件命名与目录结构应保持稳定，减少验收过程的不确定性。

### 5.5 可扩展性

- 在不改变现有分析代码前提下，系统结构应允许后续以“新增模块/新增报告段落”的方式扩展（例如新增距离度量或更多图表）。
- 扩展应遵循：产物落地 → 结构化汇总 → 报告引用 的模式，避免破坏既有 job 结构与验收标准。

## 6. 输入数据需求

### 6.1 文件与编码

- 允许 `.tsv/.csv/.txt`，建议使用 UTF-8 编码与制表符分隔（tsv）。
- 首行必须为表头；列名不应包含不可见字符。

### 6.2 abundance（丰度表）

- 必须包含特征标识列（示例为 `FeatureID`），其余列为样本列。
- 样本列名需能与 metadata 的 `SampleID` 一一对应。
- 数值为非负（计数或相对丰度均可，但不建议混用）。

### 6.3 metadata（样本信息表）

- 必须包含 `SampleID` 列。
- 至少包含一个可用于分组的变量列（供 `group_var` 选择）。

### 6.4 taxonomy（分类注释表）

- 必须包含 `FeatureID` 列，与 abundance 中的特征标识匹配。
- 建议包含常见分类层级列（如 Kingdom/Phylum/Class/Order/Family/Genus），以支持聚合到指定层级。

## 7. 输出结果需求

### 7.1 job 目录最小交付要求（验收导向）

系统每次运行应在 `results/` 下生成独立 job 目录，并至少包含：

- 输入固化：`input/abundance.tsv`、`input/metadata.tsv`、`input/taxonomy.tsv`
- 表格产物：Alpha/Beta/Diff/ML/Network/Key Taxa 等核心 CSV
- 图形产物：Alpha/Beta/Diff/ML/Network/Key Taxa 等核心 PNG（及可选 PDF）
- 结构化汇总：关键阶段的 `*_summary.json`
- AI 解释文本：`ai/` 下的 Markdown 产物（包含免责声明）
- 最终报告：`report/report.html`
- 可复现记录：`reproducibility.json`
- 日志：`logs/`（失败时至少包含错误日志）

### 7.2 输出内容边界

- 所有输出应以“统计关联与探索性发现”为主，避免将结果表述为因果关系或机制证明。
- 机器学习与网络分析输出需标注探索性性质与适用前提（样本量/类别平衡等）。

## 8. 系统约束

- 分析核心依赖既有 R 包与既有流程（如 microeco、vegan、randomForest 等）；本项目定位为上层应用与流程编排。
- AI 解释必须受约束：不得直接读取原始 abundance 表内容进行自由发挥，不得改变统计结论，不得输出因果/机制结论。
- 报告渲染依赖外部 Quarto 环境；在未正确安装 Quarto 时，报告渲染可能失败（应通过日志与提示定位）。
- 输入数据必须满足列名约定与对齐要求，否则系统应在校验阶段阻断或给出明确错误。

## 9. 验收标准

验收以“闭环完成 + 产物齐全 + 可追溯”为核心：

1. 能在 Shiny 中按规定顺序完成：上传 → 校验 → 参数保存 → 一键运行 → 预览 → 报告生成。
2. 每次运行产生独立 job 目录，且输入、参数、关键阈值与产物均落地保存，可供复核。
3. 核心产物齐全：至少包含 Alpha、Beta、差异、ML、网络、Key Taxa、AI 解释文本、最终 `report.html` 与 `reproducibility.json`。
4. 输出内容边界清晰：AI/解释文本与报告中明确声明“不做因果/机制推断”，不夸大显著性与模型能力。
5. 出现异常输入或运行失败时，系统能提供可定位的错误信息（提示与日志），且不产生误导性“成功”状态。
